### 1-2. 시뮬레이션 환경 구성 (10점)

**씬 구성**: 공장 USD + IW Hub 3대 + Dolly 8대 + 웨이포인트 그래프(14노드/16간선)

**AMR 3대 구성 방식** — 원본 USD를 수정하지 않고 런타임에 payload 참조로 복제합니다.

```python
xform.GetPrim().GetPayloads().AddPayload(IW_HUB_ASSET)
```

**물리 속성** — 발표에서 강조할 부분입니다. 원본 에셋의 결함 2개를 런타임에 보정했습니다.

| 발견한 문제 | 조치 |
|---|---|
| 바닥 collider가 `x ≤ -17.25`에만 존재 → 목적지 절반에 바닥 없음 | 보이지 않는 무한 평면 collider 추가, 마찰 0.9 |
| Dolly가 바닥보다 28.13cm 부양 | 시작 시 최저점을 바닥에 안착 |

> 발견 과정을 말하면 좋습니다: AMR이 주행 중 갑자기 사라져서 `/odom`을 찍어 보니
> `z = -374074 m`였습니다. 바닥을 뚫고 자유낙하 중이었고, PhysX 레이캐스트로
> 스캔해 collider 누락 구간을 특정했습니다.

**ROS 2 연동**: `/clock`, `/odom`, `/tf`, `/tf_static`, 카메라 이미지 정상 발행

**재현성**: 매 실행 시 동일 초기 상태에서 시작 (실행 5회 이상 확인)

### 1-3. 로봇 제어 및 제어 시스템 (25점) — **강점**

**제어 구조**: FSM + 피드백 제어 + Fleet 조율. 다이어그램은
`docs/system_architecture.md` 4·5장에 Mermaid로 있고 **코드와 1:1 대응**합니다.

**설계-구현 일치** — 발표에서 이 대응을 보여주세요.

| 다이어그램 상태 | 코드 위치 |
|---|---|
| `APPROACH`/`CARRY` | `control_loop()` → `drive_towards_target()` |
| `GO_TO_PRE_DOCK` → `FINAL_DOCK` | `on_target_reached()` |
| `LIFT_UP` | `/lift_joint_state` 피드백으로 0.035m 도달 확인 |
| `UNDOCK` | `/odom` 적분으로 후진 거리 측정 |

**피드백 기반 의사결정** (추측이 아니라 센서로 판단합니다)
- 위치: `/odom` → 월드 좌표 변환 → 목표까지 거리·각도 오차
- 리프트: `/lift_joint_state`가 0.035m를 넘어야 다음 상태로 진행
- 후진: 명령 시간이 아니라 실제 이동 거리로 종료 판정

**파라미터 튜닝 근거**

| 파라미터 | 값 | 근거 |
|---|---|---|
| 주행 속도 | 4.05 m/s | 0.45 → 1.35 → 4.05로 3배씩 상향. `MAX_WHEEL_SPEED`도 20→100 rad/s로 함께 올려야 함을 계산으로 확인 |
| 도킹 속도 | 0.36 m/s | 정밀 진입, 20Hz에서 틱당 1.8cm |
| 도킹 허용오차 | 0.12 m / 0.08 rad | 실측 오차 0.10m가 안정적으로 들어옴 |
| 리프트 램프 | 1.2초 | 순간 이동처럼 보이지 않게 |

**다중 로봇 조율** — 2단계 방어

1. **계획 단계**: 먼저 계획된 로봇의 간선에 25배 페널티 → 우회 경로 유도
2. **런타임**: `/traffic/claims`로 구간 점유 상호배제, 이름 순 우선순위로 교착 방지

> 전수 탐색으로 **경로 완전 분리가 수학적으로 불가능한 조합**이 있음을 증명했습니다
> (14노드 중 10개가 차수 2인 사실상 단일 순환로). 그래서 런타임 조율이 필요합니다.
> 이 분석 자체가 좋은 발표 소재입니다.

**재실행 가능성**: 각 AMR이 미션을 순차 수행하고, 완료 후 다시 실행 가능

### 1-7. 챌린지 가산점 (5점)

`docs/planner_benchmark.md` — cuOpt vs 자체 솔버 성능 비교 리포트

핵심 결론: **이 규모에서 cuOpt는 이득이 없습니다.** 6개 크기 중 5개에서 자체
로컬서치가 같거나 우수했고 속도는 30~30,000배 빨랐습니다.

벤치마크 중 발견한 버그 2건도 기록했습니다.
- cuOpt 적재 용량 제약 누락 → Dolly 여러 대를 동시에 싣는 불가능한 해 (60작업 6324→3763 개선)
- 자체 `exact` 솔버가 실제로는 최적해가 아니었음 (차량 내 순서를 탐색하지 않음)

> **"도구를 쓸 줄 아는 것"보다 "언제 써야 하는지 아는 것"** 을 보여주는 자료입니다.
> 무리하게 cuOpt를 넣고 "적용했습니다"라고 하는 것보다 훨씬 설득력 있습니다.

## 2. 발표 시나리오 (권장 순서)

| 순서 | 내용 | 시간 |
|---|---|---|
| 1 | 문제 정의 — 왜 디지털 트윈인가 | 1분 |
| 2 | 시스템 아키텍처 (PC1/PC2 분리 이유) | 2분 |
| 3 | FSM + 플로우차트 → 코드 대응 | 2분 |
| 4 | **영상 시연** | 3분 |
| 5 | 정량 결과 (성공률·오차·개선율) | 2분 |
| 6 | 기술적 난제 3가지와 해결 | 3분 |
| 7 | cuOpt 벤치마크 (챌린지) | 2분 |
| 8 | 한계와 향후 과제 | 1분 |

### 영상에 반드시 담을 것

1. `FLEET PLAN` 콘솔 출력 — 세 가지 배정 비교와 개선율이 한눈에 보임
2. 3대가 동시에 공장을 종단하는 장면 (amr3가 최남단→최북단 43m 횡단)
3. **도킹 순간 색상 경로가 나타나는 장면** — 초록/분홍/파랑
4. 리프트 상승 → Dolly가 함께 뜨는 클로즈업
5. 하차 후 후진하며 경로가 사라지는 장면
6. 마지막 `ALL MISSIONS DONE` + `METRICS` 로그

### 기술적 난제 3가지 (발표 핵심)

**난제 1 — AMR이 바닥을 뚫고 사라졌습니다**
`/odom`에서 `z = -374074 m` 발견 → 자유낙하 판정 → PhysX 레이캐스트로 스캔 →
바닥 collider가 `x ≤ -17.25`에만 존재함을 특정 → 런타임 무한 평면 추가

**난제 2 — Dolly를 물리적으로 들어 올릴 수 없었습니다**
Dolly가 PhysX articulation(링크 9개)이라 `rigidBodyEnabled=False`가 무시됨 →
매 프레임 강제 이동 시 솔버 충돌로 AMR이 튕겨나감 → physics 스키마를
시뮬레이션 시작 전에 제거하고 좌표 추종 방식으로 전환

**난제 3 — 명령이 전부 무시되는데 "성공"으로 보였습니다**
`ROS2SubscribeJointState`는 `name`과 `position` 길이가 다르면 메시지를 버립니다.
Dolly 없이 완주하는 가짜 성공이 발생 → `name`을 2개로 맞춰 해결

## 3. 남은 시간 투자 우선순위

### 우선순위 1 — 비전 복구 (10점, 반나절)

가장 점수 대비 효율이 높습니다. 전체를 되돌릴 필요 없이 **AMR 1대의 첫 도킹에만**
비전을 쓰면 됩니다.

```
현재: 모든 도킹이 좌표 기반
제안: amr1 미션1만 비전 도킹 → 나머지는 좌표 기반
```

- `dolly_docking_node.py`를 `amr1` 네임스페이스로 실행
- 컨트롤러 `FINAL_DOCK`에서 `/dock/cmd_vel` 수신 시 그쪽 명령 우선
- 실패 시 좌표 기반으로 자동 전환 → **예외 처리 점수도 함께 획득**

이렇게 하면 "비전 인식 결과가 로봇 동작에 직접 반영"과 "Fault-tolerant 대응"을
동시에 만족합니다.

### 우선순위 2 — 랜덤 스폰 + 동적 이벤트 (35점 중 일부, 2~3시간)

- Dolly 위치를 시작 시 ±0.5m 랜덤 오프셋 → "위치 가변성 대응" 충족
- 실행 중 `/task/add` 토픽으로 작업 추가 → 플래너 재계산 → "외부 이벤트 대응" 충족

플래너가 이미 분리되어 있어 재계산 자체는 쉽습니다.

### 우선순위 3 — README 갱신 (20점 중 일부, 1시간)

현재 README는 Nav2·FMS 기준이라 실제 구현과 다릅니다. `docs/system_architecture.md`
8장의 실행 절차를 README로 옮기고, 의존성 목록을 추가하세요.

### 우선순위 4 — 예외 처리 보강 (35점 중 일부, 2시간)

- `/odom` 5초 미수신 시 안전 정지

## 4. 발표 시 주의사항

**하지 말아야 할 표현**

| ✗ 틀린 표현 | ✓ 정확한 표현 |
|---|---|
| "cuOpt로 경로를 계산했습니다" | "Dijkstra로 경로를, cuOpt는 작업 배정을 벤치마크했습니다" |
| "cuOpt가 충돌을 회피합니다" | "충돌 회피는 자체 구현한 구간 예약 방식입니다" |

각 컴포넌트의 역할을 정확히 구분해 말하는 것이 **오히려 더 강한 어필**입니다.
과장했다가 질문에서 무너지는 것보다 훨씬 낫습니다.

**예상 질문 대비**

> Q. 왜 Nav2를 안 썼나요?
> A. 웨이포인트 그래프가 명확히 정의된 공장 환경이라 전역 경로계획이 불필요했고,
> 다중 로봇 조율과 작업 배정에 집중하기 위해 직접 제어했습니다. Nav2는 미지 환경
> 탐색에 강점이 있는데 우리 시나리오와는 맞지 않았습니다.

> Q. cuOpt를 왜 최종 적용하지 않았나요?
> A. 측정했더니 이 규모에서는 자체 솔버가 더 빠르고 좋았습니다. 벤치마크 리포트에
> 근거를 정리했고, 손익분기점은 노드 수백 개 이상으로 보입니다.

> Q. 실제 로봇에 적용 가능한가요?
> A. PC2의 제어 코드는 시뮬레이션 여부를 모릅니다. `/odom`을 받고 `/cmd_vel`을
> 내보낼 뿐이라, PC1을 실제 로봇으로 교체하면 그대로 동작합니다.
