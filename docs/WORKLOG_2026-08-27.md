# 작업 기록 2026-08-27 — 비전 기반 Dolly 도킹

전원이 갑자기 꺼져도 이어서 작업할 수 있도록, 각 단계가 끝날 때마다 갱신한다.
`docs/HANDOFF_vision_docking.md`가 세션 시작 시점의 배경이고, 이 파일은 그 이후의 실측과 결정을 담는다.

---

## 목표

AMR이 Dolly에 **도킹하기 3 m 전에 멈춰 사진을 한 장 찍고**, 그 이미지를 분석해
Dolly 위치를 확인한 뒤 진입한다. 인식 결과는 rqt로 눈에 보여야 하고,
인식이 실패해도 기존 좌표 기반 도킹으로 자동 전환되어 데모가 깨지지 않아야 한다.

## 완료된 단계

### 1. WaypointGraph(바둑알 마커) 제거 — 완료

카메라 시야를 가리던 웨이포인트 마커를 씬에서 제거했다.

- 파일: `simulation/isaac_sim/standalone_factory_bridge.py` → `hide_waypoint_graph()`
- **기존 방식이 왜 안 통했나**: `UsdGeom.Imageable.MakeInvisible()`은 호출한 프림에만
  의견을 기록한다. 하위 마커 메시들이 자기 visibility를 따로 갖고 있어서,
  `Nodes`/`Edges` 두 Xform은 "숨겼다"고 로그를 찍으면서도 구슬들은 계속 렌더됐다.
- **바꾼 방식**: 루트 `/World/WaypointGraph`를 `SetActive(False)`로 **비활성화**.
  컴포지션에서 서브트리째 빠지므로 하위 의견이 덮을 수 없고, 뷰포트와 Stage 트리에서도 사라진다.
- 안전성: 플래너가 노드 좌표와 엣지를 모두 읽은 **뒤에** 호출된다
  (`load_waypoint_graph()` 다음). 원본 USD는 저장하지 않는다.
- 되돌리기: `SHOW_WAYPOINT_GRAPH=1`

확인된 로그:
```
[WAYPOINT GRAPH] deactivated /World/WaypointGraph: Nodes(14), Edges(16)
```

### 2. 카메라 화각 30.5° → 60° — 완료

- 파일: `scripts/scale_intrinsics.py` (화각 인자 추가)
- 사용법: `python3 scripts/scale_intrinsics.py 640 360 60`
- 저작된 카메라는 fx=2344 @1280, 즉 **수평 FOV 30.5°의 망원**이었다.
  폭 3.16 m인 Dolly 상판이 도킹 거리에서 화면을 완전히 넘겨, 잘리지 않는 구간이 없었다.
- 스크립트가 목표 화각으로 fx, fy를 다시 만들고 주점을 화면 중앙으로 재설정한다.
  브릿지는 `aperture = focal * width / fx`로 USD 조리개를 유도하므로 이 파일 하나만 바꾸면 된다.
- 효과: 흰 벽만 확대되던 화면에서 **파란 상판 + 검은 캐스터**의 Dolly가 또렷하게 보이게 됐다.

확인된 로그:
```
projection_from_intrinsics=fx=554.256, fy=554.256, aperture=(0.230940, 0.129904)
```

### 3. 학습된 YOLO 가중치 평가 — 사용 불가로 판정

`dolly_pose_v1_best.pt` (Downloads의 파일과 md5 동일: `30e48960...`)

실주행 캡처로 측정한 결과 (`/tmp/cap`, `/tmp/cap60`):

| 화각 | 최고 conf | 프레임당 검출률 |
|---|---|---|
| 30.5° | 0.40 | 35프레임 중 3회 (~9%) |
| 60° | 0.71 | 20~30% |

conf 임계값을 0.05로 낮추면 **완전히 검은 프레임 21개 전부**에서 Dolly를 검출한다.
낮은 임계값의 검출은 신호가 아니라 잡음이다.

**근본 원인 — 학습 라벨의 기하가 실제 Dolly와 다르다.**
실측 프레임에서 파란 상판의 픽셀을 월드 좌표로 환산하면 z ≈ **0.85 ~ 1.15 m 이상**인데,
`vision_config.DOLLY_KEYPOINTS_LOCAL`은 P1~P4를 z=0.230, P5~P8을 z=0.470에 둔다.
즉 학습 키포인트는 실제 Dolly의 **절반 높이**, 바퀴·차축 근처를 가리킨다.
SDG가 이 키포인트를 투영해 bbox 라벨을 만들었으므로 **학습 라벨 자체가 Dolly 본체가 아니라
그 아래 바닥에 그려져 있었다.** `scripts/project_dolly.py` 오버레이에서 P1~P8이
파란 상판이 아니라 바퀴 사이 바닥에 찍히는 것으로 눈으로도 확인된다.

따라서 임계값 조정으로는 해결되지 않고, 검출되더라도 `solvePnP` 자세는 설계상 틀린다.
TTA는 yolo26n이 미지원, 입력 업스케일(960/1280)도 개선 없음.

**결정: HSV 색 기반 검출로 전환.** (재학습은 키포인트 수정 + SDG 재생성부터 필요)

### 4. HSV 파란 상판 검출기 — 완료

- 파일: `simulation/isaac_sim/vision_docking/runtime/blue_deck_detector.py`
- Dolly 상판은 흰 바닥·회색 설비뿐인 공장에서 유일하게 채도 높은 파랑이다.
  단일 HSV 범위 `(95,80,50)~(130,255,255)`로 1~8 m에서 **80~100%** 분리된다.
- **거부 게이트는 전부 실측 실패에서 나왔다**:
  - `clipped at frame edge` — f_0038은 상판을 정확히 잡지만 왼쪽 화면 밖으로 잘려
    중심이 실제 방위보다 28° 왼쪽에 찍힌다.
  - `too small` — f_0029는 프레임 밖 Dolly의 2306px 조각을 잡고 47° 틀린다.
  - `not deck-shaped`, `too low in frame` — 배경 설비 배제
  - `blank frame` — Isaac이 간헐적으로 내보내는 완전 흑색 프레임
- **방위(bearing)만 보고한다.** 방위는 fx와 cx만으로 정해지고 둘 다 우리가 저작한 값이라
  숨은 가정이 없다. 거리는 보고하지 않는다:
  - 겉보기 폭에서 구하려면 상판 폭 상수가 필요한데, 실측 피팅은 3.29 m를 냈다.
    뒤에 줄지어 선 Dolly가 같은 파란 덩어리로 합쳐지기 때문이다.
  - 바닥 평면에서 구하려면 카메라 높이·피치가 필요한데, 브릿지 상수로 투영하면 눈에 띄게 어긋난다.
  - 거리는 이미 오도메트리로 알고 있으므로 추정할 필요가 없다.

### 5. 스냅샷 노드 + 컨트롤러 연동 — 완료, 2대 전 미션 검증됨

- `simulation/isaac_sim/vision_docking/runtime/dolly_snapshot_node.py`
  - 요청: `/dock/snapshot_request` (String JSON, seq 포함)
  - 응답: `/dock/snapshot_result` (String JSON, seq 에코)
  - 디버그 영상: `/vision/dolly_docking/debug_image` — 요청과 무관하게 **상시 발행**
    (rqt에서 계속 보이도록). 검출 성공 시 초록 박스, 거부 시 빨간 박스와 사유.
  - 정지 상태에서 5프레임을 모아 **중앙값** 방위를 답한다.
- `ros2_ws/src/amr_control/amr_control/amr_mission_controller.py`
  - 새 상태 `VISION_STANDOFF` → `WAIT_SNAPSHOT` → `GO_TO_PRE_DOCK` → `FINAL_DOCK`
  - 도킹 축을 따라 `snapshot_standoff_m` 뒤에서 **정지** 후 촬영 요청
  - 결과를 측방 보정으로 환산해 `snapshot_max_correction_m`(기본 0.10 m)로 **클램프** 적용
  - 실패·타임아웃·방위 과다 → 보정 없이 기존 좌표 도킹으로 진입
  - 보정값은 미션마다 초기화 (다른 Dolly의 보정이 새 나가지 않도록)
- 활성화: `-p vision_dock_mission:=0` (해당 미션에서만 비전 사용)

**정확도에 대한 정직한 한계** — AMR이 Dolly를 정면으로 겨눈 프레임 기준 방위 오차:

| 프레임 | 거리 | 상판 오차 | 캐스터 오차 |
|---|---|---|---|
| f_0043 | 2.68 m | — | 0.0° |
| f_0044 | 2.55 m | — | +2.4° |
| f_0214 | 3.12 m | — | −0.9° |
| f_0213 | 3.61 m | −2.7° | −3.3° |
| f_0212 | 4.09 m | −4.2° | −4.7° |

3 m 기준 측방 0.05~0.30 m. 현행 좌표 도킹 실측 오차는 0.09~0.12 m이므로
**보정을 무제한 적용하면 오히려 나빠진다.** 그래서 ±0.10 m 클램프를 둔다.
비전의 역할은 "Dolly가 실제로 거기 있고 대략 중앙에 있다"는 **진입 허가 판정**이 주이고,
보정은 제한된 보조다.

### 6. 스탠드오프 기준점 수정 — 완료

첫 통합 실행에서 스냅샷이 매번 `clipped at frame edge`로 거부됐다.
원인은 `snapshot_standoff_m`을 **dock 지점 기준**으로 쟀기 때문이다.
dock 지점은 Dolly 아래 중앙이므로, 3 m 뒤에 서면 Dolly 앞단은 훨씬 가깝다.

브릿지가 Dolly 바운딩 박스를 인벤토리에 기록하도록 했다
(`standalone_factory_bridge.py`, `world_bounds_of_prim` 사용):

```
01. /World/dolly_physics | ... | size=(0.86, 1.24, 0.49)
02. /World/dolly_physics_01 | ... | size=(1.24, 0.86, 0.49)
```

**Dolly 실측 크기는 1.24 × 0.86 × 0.49 m다.** 앞서 이미지에서 3.16 m로 추정했던 것은
틀렸다 (배경의 파란 설비가 붙은 덩어리를 잰 것이었다).

컨트롤러는 이제 스탠드오프를 **Dolly 앞단 기준**으로 계산한다:
```
back_off = 요청 여유거리(3.0) + Dolly 반깊이 + 카메라 전방 오프셋(0.55)
```
`deck_width_across()` / `deck_depth_along()`이 dock 방위로 바운딩 박스를 투영한다.
AMR은 Dolly의 짧은 축(0.86 m)을 따라 진입하므로 카메라가 보는 폭은 **긴 쪽(1.24 m)**이다.
처음에 `min(size_x, size_y)`를 써서 0.86을 넘겼던 실수를 바로잡았다.

### 7. 검출기 2단계 분리 — 완료

여러 방식을 실측으로 전부 시험한 결과:

| 방식 | 정면 조준 시 오차 | 이상치 |
|---|---|---|
| YOLO (현 가중치) | 검출률 20~30% | conf 0.05에서 흑색 프레임 100% 오검출 |
| 상판 중심 | ±5° | −28° (잘림) |
| 캐스터 중점 | ±5° | −34° |
| 예상 폭 게이트 | — | 전부 거부 |
| 최하단 파란 띠(깊이 순서) | ±3° | +26°, −25° |

**결론: "Dolly가 있다"는 판정은 확실하지만(75~100%), "정확히 어디인지"는 색만으로 안 된다.**
공장 통로의 파란 설비가 상판과 같은 색이라 하나의 연결 성분으로 합쳐진다.
3.5 m에서 예상 폭 201 px인데 실제 덩어리는 501 px로 관측된다. 깊이 정보 없이는 분리 불가.

그래서 `Detection`을 두 필드로 나눴다:
- `present` — Dolly가 앞에 있는가. **신뢰 가능.** 진입 허가 판정에 쓴다.
- `ok` — 방위를 조향에 써도 되는가. **드물게만 참.** 보정에만 쓴다.

rqt 오버레이 색으로도 구분된다: 초록=측정해 반영, 노랑=확인됐으나 측정 불가, 빨강=없음.

### 10. 진짜 원인 — 렌더링 화각이 설정값과 다르다

실주행 프레임에서 상판이 잘리지 않은 5장을 골라, 알려진 거리와 실제 픽셀 폭으로
유효 fx를 역산했다:

```
range=5.55 m  w=342px  -> fx = 1529
range=5.07 m  w=366px  -> fx = 1493
range=4.58 m  w=393px  -> fx = 1449
range=4.09 m  w=439px  -> fx = 1447
range=3.61 m  w=505px  -> fx = 1467     중앙값 1467

설정값 fx = 554 (60도),  저작 카메라 30.5도를 640폭으로 환산하면 1172
```

폭이 거리에 정확히 반비례한다(fx 편차 3%). **단일 강체를 올바르게 보고 있다는 뜻**이므로,
"배경 파란 설비와 병합됐다"는 §7의 해석은 틀렸다.
문제는 **함의된 fx 1467이 설정값 554와 2.6배 다르다**는 것이다.

브릿지 로그는 `projection_from_intrinsics=fx=554.256, aperture=(0.335640, 0.188797)`을
찍지만, 실제 렌더 결과는 그 조리개를 따르지 않는다.

**이 하나가 오늘의 모든 측정을 조용히 오염시켰다.** 방위 오차 20~35°,
"예상 폭 게이트 전부 거부", "깊이 순서 이상치" — 전부 이 스케일 오차의 증상일 수 있다.

### 11. 카메라 투영 보정 — 해결, 카메라 기반 도킹 작동

**렌더러는 USD 광학 속성을 무시한다.** 초점거리를 0.2364에서 0.2로 바꿔도
측정된 fx는 1286.3 → 1285.8로 사실상 동일했다. 조리개를 바꿔도 마찬가지였다.
즉 이 카메라는 우리가 무엇을 설정하든 **28° 고정**으로 렌더링한다.

그래서 강제하는 것을 포기하고 **측정해서 기록하는 방식**으로 바꿨다.

- `standalone_factory_bridge.py`: `FORCE_CAMERA_OPTICS` 플래그 추가, **기본값 off**.
  이제 저작 광학을 그대로 두고, intrinsics 파일은 "실제로 나오는 렌즈의 서술"로만 쓴다.
- `camera_intrinsics_640.npz`: `fx = fy = 1286.3`, `cx = 320`, `cy = 180` (실측)
- `blue_deck_detector.BEARING_BIAS_DEG = 2.01` — 상판 파란 중심과 Dolly 원점 사이의
  계통 편차. 53장에서 +2.04°로 일관되게 측정됐다 (노이즈가 아니라 장착 오프셋).

**결과 — 방위 오차가 sd 약 19° 에서 2.6° 로 떨어졌다.**

| | 보정 전 | 보정 후 |
|---|---|---|
| 방위 오차 중앙값 | −5.2° | 0.00° |
| 표준편차 | 19.3° | 2.63° |
| 3 m 기준 측방 오차 | 3.5 m | 0.138 m |
| 검출 수락률 | 0% | 56% |

오늘의 잘못된 결론 두 개가 이 하나에서 나왔다:
"배경 파란 설비와 병합된다"(§7)와 "상판 폭이 3.29 m다"(§10 이전).
둘 다 2.6배 틀린 카메라 모델의 증상이었다. 마스크를 실제로 그려보면
**파란 영역은 Dolly 상판만 덮고 배경은 전혀 물지 않는다.**

### 13. 튜닝과 최종 실증 (GUI + rqt)

스탠드오프 자세 허용오차를 2°로 풀었더니 보정이 오히려 해로웠다:
기대 방위가 −1.88°로 계산되고 카메라는 +0.02°를 봐서, **자세 오차가
측방 오차로 오해석**됐다. 보정 +0.182 m가 나와 클램프 0.10 m가 걸렸고,

### 15. 후진 제거 + 오버레이 색 통일

**문제 1 — Dolly 앞까지 갔다가 뒤로 5 m 물러난 뒤 다시 들어갔다.**

경로 종점 Node_10은 y=22.50, dock은 y=25.84, 스탠드오프는 y=20.26이다.
즉 스탠드오프가 Node_10보다 2.2 m **뒤**에 있어서, 경로가 데려다 놓은 뒤에
후진해야 했다. Node_10에서 바로 찍을 수는 없다 — 거리 2.47 m에서 상판이
`1286 × 1.242 / 2.47 = 647 px`로 640 px 화면을 넘긴다.

`maybe_snapshot_on_approach()`를 추가해 **접근 주행 중** dock까지 거리가
스탠드오프 거리 아래로 처음 내려가는 순간 멈추게 했다. 전진만으로 도달한다.

**문제 2 — 그 지점에서 검출 실패 (318 px 예상, 70 px 관측).**

멈추기만 해서는 부족했다. 접근 경로가 남긴 헤딩 그대로라 Dolly가 화면 옆으로
밀려 있었다. `SNAPSHOT_ALIGN` 상태를 넣어 제자리에서 dock 방향으로 자세를 맞춘
뒤 촬영한다. 1초 정도 들지만, 워크로그의 모든 방위 수치가 측정된 조건과 같아진다.

```
STANDOFF reached on approach at 5.58 m from dock, turning to face the Dolly
STANDOFF aligned to 90.0 deg, taking snapshot
SNAPSHOT DOLLY CONFIRMED on 5/5 frames
SNAPSHOT hold done, resuming approach
DOCK OK | position_error=0.116 m
```

**문제 3 — 오버레이가 주황색으로 떠서 실패처럼 보였다.**

원래 초록(방위까지 조향 반영) / 주황(존재만 확인)으로 구분했는데,
그 구분은 컨트롤러가 그 값을 어떻게 썼느냐에 관한 것이고 **인식 성공 여부와는
무관하다.** 5/5 프레임에서 검출된 Dolly 앞에서 주황 박스가 뜨면 보는 사람에게는
실패로 읽힌다. 검출되면 무조건 초록으로 바꾸고, 구분은 하단 작은 글씨로 옮겼다.

### 카메라 도킹을 3대 전부로 확장 (B안) — 미착수

지금은 도킹 카메라가 **첫 번째 로봇에만** 붙는다:
```python
robot_path = find_robot_root(stage)
camera_path, ... = create_docking_camera(stage, robot_path, ...)
build_camera_bridge(camera_path)     # 토픽 1개: /vision/front_camera/image_raw
```
스냅샷 요청/응답 토픽(`/dock/snapshot_request`)도 전역이라 AMR이 여럿이면 교차 수신한다.

필요 작업 (예상 2~2.5시간):
1. 브릿지: AMR별 도킹 카메라 + render product + 토픽 네임스페이스 (45~60분)
   — `topic()` 헬퍼가 이미 `cmd_vel`/`odom`에 쓰이므로 같은 방식으로 붙일 수 있다
2. 스냅샷 노드: 토픽 파라미터화 후 3개 인스턴스 (15분)
3. 컨트롤러: 요청/응답 토픽 AMR별 분리 (15분)
4. 3대 6미션 통합 테스트 (45분)

**GPU 위험**: render product가 1개 → 3개. 이미 드라이버 과부하로 튕긴 이력이 있다.
완화책은 스탠드오프 도착 시에만 카메라를 켜는 방식이지만 위 견적에 포함되지 않았다.

```
SNAPSHOT DOLLY seen at +X.XX deg (expected ...) -> lateral +X.XXX m, applying +X.XXX m
```

### 주요 파라미터
| 파라미터 | 기본값 | 의미 |
|---|---|---|
| `vision_dock_mission` | -1 | 비전을 쓸 미션 index (0-based), -1이면 비활성 |
| `snapshot_standoff_m` | 3.0 | Dolly **앞단**에서 카메라까지 여유 거리 |
| `snapshot_dwell_sec` | 2.0 | 인식 후 정지 유지 시간 (시연용) |
| `snapshot_max_correction_m` | 0.10 | 측방 보정 클램프 |
| `snapshot_max_bearing_deg` | 12.0 | 이 각도를 넘으면 측정을 신뢰하지 않음 |
| `save_rejected_dir` | `/tmp/snapshot_rejects` | 거부된 프레임과 마스크 저장 (진단용) |

## 유의사항

- 이 세션의 백그라운드 프로세스는 **`setsid`로 분리**해야 한다.
  `nohup`만으로는 호출한 bash 툴이 타임아웃될 때 프로세스 그룹째 죽는다. 실제로 두 번 겪었다.
- `factory_inventory.json`의 Dolly 좌표는 **브릿지 기동 시점** 값이다.
  주행 중 Dolly가 옮겨지면 이 값은 낡은 값이 되므로, 검증 스크립트의 정답으로 쓸 때
  첫 픽업 이전 구간만 신뢰할 수 있다.
- 카메라 해상도를 바꾸면 반드시 `scripts/scale_intrinsics.py`로 intrinsics를 다시 만들 것.
  안 그러면 브릿지가 조리개를 다시 유도하면서 화각이 조용히 바뀐다.

### 중요 — 프로세스를 죽이는 것은 run_bridge.sh가 아니다

`scripts/run_bridge.sh`에는 `kill`, `pkill`, `rm` 구문이 **하나도 없다**
(`grep -cE "pkill|killall|kill -" scripts/run_bridge.sh` → 0).
프로세스를 정리하는 것은 별도로 실행하는 `scripts/cleanup.sh`다.

**컨트롤러 코드만 바꿀 때는 브릿지를 끄지 않아도 된다.** 컨트롤러만 재시작하면
Isaac Sim GUI가 유지되므로, GUI를 반복해서 죽였다 띄우다가 GPU 드라이버가 리셋되고
우분투 세션이 로그아웃되는 현상을 피할 수 있다.

```bash
for p in $(pgrep -f "amr_mission_contro[l]ler"); do kill -9 "$p"; done
```

단, 시뮬 상태(Dolly 위치)는 초기화되지 않는다. 이미 옮긴 Dolly를 다시 가지러 가면
`no blue region`이 나오는데 이는 정상 동작이다 — 없는 것을 없다고 보고한 것이다.

### 되돌린 변경 (다시 시도하지 말 것, 하려면 신중히)

`smooth_angular()`의 최소 회전속도 하한(0.13 rad/s)과 가속 제한(1.2 rad/s²)을
함께 넣으면 **제자리 회전이 수렴하지 못한다.** 0.022 rad 허용오차 안에서 하한이
계속 회전을 강제하고, 가속 제한이 반전에 여러 틱을 쓰기 때문이다.
amr2가 목표에서 멀어지는 것(-1.873 → -2.029 rad)이 관측되고 amr1은
`SNAPSHOT_ALIGN`에서 나오지 못했다.

현재는 `angular_gain=1.2`, `min_angular_speed=0.0`, `max_angular_accel=1000`으로
사실상 기존 비례 제어로 되돌려 둔 상태다. 부드럽게 만들려면 하한을 상수로 두지 말고
최종 접근각 안에서 함께 줄어들게 해야 한다.

## 진행 중 — YOLO 재학습용 SDG

배경막을 끄고 실제 공장에서 렌더링하도록 바꾼 뒤 **200회 시도 0장 저장**.
거부 사유 집계를 SDG에 추가해 원인을 특정했다.

**1차 원인 (수정 완료)**: `USE_FIXED_CAMERA_BASIS = True`가 카메라 광학축을
+X로 하드코딩하고 있었다. 실제 이 카메라의 마운트는 **yaw = −90도**라 −Y를 본다.
Dolly를 90도 어긋난 곳에 배치하고 있었던 것이다.

배경막이 있을 때 이 오류가 숨어 있던 이유: 배경막도 같은 잘못된 forward 벡터로
배치돼서 항상 Dolly 뒤에 나타났다. **배경막 제거가 이 버그를 드러냈다.**

기본값을 `False`(카메라 변환에서 유도)로 바꾼 결과:
```
이전: too few visible keypoints=200
지금: too few visible keypoints=104, bbox too far off centre=96
```

**남은 작업**: 절반은 공장 구조물에 가려지고, 절반은 화면 중앙에서 벗어난다.
다음에 확인할 것 —
1. `right_xy` 부호와 lateral offset 방향이 맞는지 (중앙 이탈 96건의 원인 후보)
2. 카메라 위치가 AMR 스폰이라 앞에 구조물이 있는지. Dolly가 실제로 놓이는
   빈 통로 좌표에서 렌더링하도록 `camera_position` 산출을 바꿀 필요가 있는지
3. `MIN_VISIBLE_KEYPOINTS = 4`가 이 씬에 적정한지

## 스냅샷 표본 확대 + 도색선 오검출 수정

### 바닥 도색선을 Dolly로 오인 — 수정

통로 바닥의 파란 도색선이 상판과 같은 HSV 범위에 들어와, 가장 넓은 파란 덩어리가
도색선인 경우가 있었다. **놓친 검출보다 확신에 찬 오답이 더 나쁘다** —
보는 사람이 구분할 방법이 없다.

색으로는 불가능하지만 형상으로는 가능하다. 상판은 두께 0.257 m로
스냅샷 거리 3~5 m에서 66~107 px, 도색선은 몇 px에 통로 폭만큼 길다.
`MIN_HEIGHT_PX = 14`, `MAX_ASPECT_RATIO = 14.0` 추가. **존재 판정에도 같은 게이트를
적용**했다 — 그러지 않으면 방위는 거부하면서 배너는 계속 `DOLLY DETECTED`라고 한다.

567프레임 회귀:

| | 수정 전 | 수정 후 |
|---|---|---|
| Dolly 시야 내 검출 | — | 91/92 (99%) |
| 빈 프레임 보고 | 53건 | 8건 |

남은 8건을 열어보니 **전부 실제 Dolly가 화면에 있었다.** 판정 기준(±20°/20 m)이
좁아서 "없다"로 분류한 것이고 검출기가 맞았다. 실질 오검출 0건.

## 검증되지 않은 변경 (다음 세션에서 확인 필요)

### 1. `deck_width_across()` — 빌드됐으나 미검증

`no blob near 350 px wide` 실패를 쫓다가 두 번 고쳤다.

- **1차 시도(실패)**: Dolly yaw로 footprint를 투영해 정확한 폭을 예측하려 했다.
  더 나빠졌다 — `dolly_footprint()`가 반환하는 값은 **이미 월드축 바운딩 박스**라
  회전이 반영돼 있는데, 거기에 yaw를 또 적용해 **회전을 이중 계산**했다.
  0.865 m를 예측했으나 실제 관측은 397 px @ 4.0 m = **1.235 m**(긴 변)였다.
- **2차(현재)**: 정확한 예측을 포기하고 **최대 가능 폭**(긴 변)을 쓴다.
  게이트의 목적은 측정이 아니라 3 m짜리 배경 병합 블롭 거부다. 허용오차 ±45%가
  짧은 변(0.865/1.242 = 0.70)까지 덮으므로 두 방향 모두 통과한다.

**미검증 이유**: 브릿지를 살려둔 채 컨트롤러만 재시작해 검증하려 했으나,
Dolly가 이전 주행에서 이미 옮겨진 뒤라 `no blue region`이 나왔다.
**검출기가 맞았고 씬이 낡았다.**

### 2. 씬 리셋 — 헬퍼만 있고 배선 안 됨

`capture_reset_state()`, `restore_reset_state()`, `poll_reset_request()`를
`standalone_factory_bridge.py`에 추가했으나 **메인 루프에 연결하지 않았다.**
현재는 죽은 코드다. 남은 작업:

1. 초기화 직후 `capture_reset_state(stage, dolly_paths, amr_paths)` 호출
2. 메인 루프에서 `poll_reset_request()` 확인 → `restore_reset_state()`
3. 컨트롤러도 미션 인덱스를 0으로 되돌려야 함 (리셋 토픽 구독 필요)

**이 기능이 없어서 오늘 반복 비용이 컸다.** 수정 하나를 검증할 때마다 브릿지를
40초 재기동해야 하고, 그 과정에서 낡은 로그를 새 실행으로 착각해 잘못 판단한 일이
두 번 있었다. 다음 세션에서 **가장 먼저 할 일**로 권한다.

### 3. 브릿지 자체 종료

두 번 관측했다. 한 번은 555초 후 `Simulation App Shutting Down`,
한 번은 로그가 그냥 멈췄다. GPU 메모리 경고만 반복되고 원인은 로그에 없다.
**발표 중 발생하면 데모가 끊긴다.** 시연 영상을 여유 있게 미리 녹화할 것.
